A **conforming implementation** is one that, given these vectors, reaches
the same verdicts. There are two graded levels, the floor reachable today
by an implementation in any language with an Ed25519 library, the ceiling
reachable only by a port of the engine — the pattern KYA-OS's conformance
suite uses, and the one this file follows.

## L1 — the bytes

What is checked: for every one of the 143 vectors (45 and 98), the act's signature(s)
verify over the entry's recorded `body` under the holder's `did:key` —
Ed25519 over the UTF-8 bytes of `sha256:<hex>` of the canonical body
(`spec/signing.md` §4 rules 2 and 3 — the digest and the Ed25519 step; rule 1, body = object minus `signature`, does NOT apply: a city door's body is its own projection, carrying the realm and the tick the act does not, which is what makes it single-use — the passport alone is object-minus-signature; the signature is `ed25519:<base64url>`, the key is
`did:key:z6Mk…`, Ed25519 multicodec `0xed01`). A landing must verify on
every signature it carries; a refusal must **not** — at least one of its
signatures was made for the realm `nowhere:Elsewhere:0`, or under another
holder's key where the body carries no realm (the countersignature), and
verifies under nobody.

Which signatures a kind carries (the shapes of `Bodies` in `present.ts`):

| kind | signatures, and the body each is over |
|---|---|
| `admit` | `passport.signature` over `body.passport`; `opening.signature` over `body.opening` — both under `passport.did` |
| `answerEscalation` | `signature` over `body.answer`; with a `grant`, `grant.signature` over `body.grant` |
| `nameArbiter` | `signatures.claimant` over `body.claimant` under the key of `signers.claimant`; `signatures.respondent` over `body.respondent` under the key of `signers.respondent` — the entry names both signers by label in `holders`, and each half is verified under the named key and no other (an entry without `signers` fails L1) |
| `adopt` | `signature` over `body.adoption`; `opening.signature` over `body.opening` — both under the act's `did` |
| `countersign` | `signature` over `body`, the delegation payload (no realm, no tick) |
| `register` | `signature` over `body` under `request.did` — the applicant has no principal yet, so the key is the request's own |
| every other kind | `signature` over `body`, one string |

To conform at L1, an implementation does two things. First, it verifies
the recorded bytes as above and reaches the same 143 verdicts — that is what
`npm run conform` prints as `L1 143/143`, and it needs no simulation at all.
Second, on its own side, it **reproduces each `body`** from the act and the
entry's `world.realm` and `world.tick` — the canonical encoding of
`docs/DOORS.md`'s body functions, sorted keys, no whitespace — and finds
it byte-equal to the recorded one. The runner cannot check the second half
for a foreign implementation; a foreign implementation that reproduces the
bodies has proven it would sign, and refuse, what this engine signs and
refuses.

## L2 — the doors

What is checked, per file: the world the file describes is founded
(`start`: seed, population, size and layout when set, mind, governor),
stepped to `start.tick`, and must hash to `start.hash`; then every entry in
order — the `ticks`, `authorize` and `foundFirm` steps applied and their
recorded tick, decision, row, mandate, firm and hash asserted; and for
every vector, the world's hash before it, `bodyOf(world, act)` equal to the
recorded body, the door's verdict, the subjects of what landed (and that
the rows reported are the rows the chain gained), or the refusal's
sentence and the hash and the chain unmoved.

Only a port of the engine reaches L2: the hashes are the engine's, the
subjects are the doors' own rows, and the sentences are the doors' own
words. When the runner founds a world whose hash is not the file's
`start.hash`, it reports `L2 n/a: start hash <x> is not this world` and
runs L1 alone — the file is then the record of another world, not a
failure of this one.

## Running it

```
npm run conform                                       # public/doors/vectors.json and vectors-small.json
npm run conform -- --vectors path/to/vectors.json     # one file alone; repeat --vectors for more
npm run conform -- --vectors https://…/vectors.json   # fetched
```

The output is one header line per file (its realm, seed, population,
layout when set, tick and start hash; `L2 n/a on <file>: …` when its
world is not this one), a per-door table over every file — forty-six
rows, `door | landing L1/L2 | refusal L1/L2 | file`, `×n` where a door has
more than one landing or refusal on file, the last column naming the file
or files its vectors came from, `no vector on either file` for a kind
neither carries — a `FAIL <file> #<entry> <kind>: <why>` line for anything
wrong, and one badge line:

```
doors 45/46 · vectors 143/143 · L1 143/143 · L2 143/143 · start dcfd3ea898480a4d / 72634628faf93840 · engine <git short sha>
```

The credential the hire doors read — the label, the levels, the chain rows a verifier checks — is published at `public/credentials/schema.json` with its rules in `public/credentials/README.md` (C-15).

`doors` counts the kinds whose landing and refusal both pass at every
level that ran, on whichever file carries them, out of the catalogue's
forty-six (45 while `fundGuild`'s landing is pending); `vectors` the entries that pass, summed over the files; `L1`
and `L2` the entries passing at that level (`L2 n/a` when it ran on no
file; `L2 15/15 (n/a on vectors.json)` when it ran on one file and not the
other, and the head counts then say `(L1)`); `start` each file's start
hash, in the files' order; `engine` the commit of the engine that ran.
Exit 0 when every row passes at every level that ran; exit 1 on any FAIL;
exit 2 when a file cannot be read. Nothing in the output comes from the
clock — the same files on the same commit print the same lines.
`tests/present.test.ts` and `tests/conform.test.ts` run the same replayer.

## What a badge claims, and what it does not

`L1 143/143` says: the signatures on file are what the files say they are —
every landing verifies, every refusal does not — under the keys the files
name. Presented by a foreign implementation, it says that implementation's
signature check agrees with the engine's on these 143; with the bodies
reproduced on its side, that it computes the same bytes to sign.

`L2 143/143` says: this engine, at this commit, is the engine both files were
recorded on — the same two worlds, the same doors, the same rows and
sentences.

What neither says:

- **The badge is self-reported.** Nothing signs it. A line of text printed
  by a runner is a claim by whoever ran it; anyone who wants to know runs
  the runner on the file themselves.
- **Every refusal on file is a signature refusal** — a signature made for
  another realm, or under another key. L1 passes a refusal *because* its
  signature does not verify. A refusal for another reason — a door's
  sequence, standing or band check, refused with a signature that verifies —
  would fail L1 by construction, not pass it. Two rows on the small file
  (#33 `appealHire`, #34 `evaluateAppeal`, 2026-09-17) are refused by the
  door for a state reason before it reads the signature — the task is not
  appealable, the hire is not appealed — and are *also* signed for another
  realm, which is what L1 checks; the recorded sentence is what L2 asserts.
  So are #60 `sanction` (rung 3 when the ladder stands at 1) and #62
  `writeWork` (the accused under a rung-2 bar), C-5, 2026-09-17; and #88
  `sponsorAdmission` (the guild forming), #106 `claimRelief` (the gap),
  #107/#108 `fundGuild` (not a member; the pool whole) and #112
  `offerCredit` (one cent over the cap), C-6/C-11/C-12, 2026-09-17 — all
  also signed for another realm, so L1 passes them.
  A refusal with a signature that verifies needs a level of its own, not
  this one bent around it.
- **L1 verifies under the key the file names, not the key the door
  reads.** For one-signature acts the file names the holder and the door
  verifies under the same DID, so the two agree. For `nameArbiter` the file
  names both signers (`signers`) and L1 verifies each half under the named
  key and no other — but that the named respondent *is* the dispute's
  respondent in the world is L2's to establish, from the dispute record;
  L1 establishes only that the file's own labels and signatures agree.
- **A recorded body that is not a string is a FAIL on a refusal too** —
  "nothing to refuse" — never a vacuous pass: a refusal is passed by a
  signature that does not verify over real bytes, not by the absence of
  bytes to verify.
- **A `foundFirm` step is a fixture, not a door.** The small file's hirer
  comes to own a firm by the hire test's own means — a closing, a stake
  from the treasury, a founding mandate signed under a public seed — which
  the runner replays and asserts (the mandate id, the firm id, the hash
  after). A badge over that file says the doors after it behave as
  recorded on that world; it says nothing about how a firm is founded.
- **`engine` is meaningful only on a clean tree.** With uncommitted changes
  the runner prints `<sha>-dirty`; such a badge names no commit anyone else
  can check out and is not reproducible. A badge worth quoting is one whose
  `engine` is a bare sha.

Neither says the doors are right. The vectors are a record of what the
engine does, not a proof of what it should do; a door with a wrong rule
records its wrong rule, and a badge over that file certifies the
agreement, not the rule. Neither says anything about doors the file does
not reach — the laws that take no signature (`haltByLaw`, the scheduled
steps), `authorize` (a gate, not a door), or a refusal the file does not
carry: at least one refusal per kind is on one file or the other, and each
door has more. And a badge is a run on two worlds, each from one tick; an
implementation that passes it has shown it opens these doors on these
records, and nothing about the next world.

The key seeds in `holders` are public; those DIDs are test identities and
must never hold value.
